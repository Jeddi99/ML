อ่านไฟล์นี้จบ คุณจะเล่าโปรเจกต์นี้ให้ใครฟังก็ได้ แม้ไม่เคยทำเอง
เขียนแบบเล่าให้เด็กฟัง ใช้การเปรียบเทียบ ไม่มีโค้ด ตัวเลขทุกตัวถูกต้องตรงกับงานจริง

## 0. ถ้ามีเวลาอ่านแค่ 1 นาที อ่านตรงนี้

**เราทำอะไร:** สร้างโปรแกรมที่ดูข้อมูลลูกค้าค่ายมือถือ แล้วบอกว่า "คนนี้มีโอกาสย้ายค่ายกี่เปอร์เซ็นต์"

**ทำไปทำไม:** บริษัทมีลูกค้าเป็นพัน แต่พนักงานที่โทรง้อลูกค้ามีไม่กี่คน ต้องรู้ว่าควรโทรหาใครก่อน

**ทำอย่างไร:** เอาข้อมูลลูกค้าเก่า 7,043 คน ที่รู้แล้วว่าใครย้ายใครอยู่ ให้คอมพิวเตอร์เรียนรู้รูปแบบ แล้วเอาไปทายลูกค้าใหม่

**ได้ผลแค่ไหน:** จับคนที่จะย้ายค่ายได้ 78 จาก 100 คน และเอาไปทำเป็นเว็บใช้จริงได้แล้วที่ jeddilok.pythonanywhere.com

**เรียนรู้อะไร:** ตัวเลขความแม่นยำหลอกเราได้ / สิ่งที่คิดว่าจะช่วยอาจไม่ช่วย / ต้องวัดผลทุกอย่าง ไม่ใช่เชื่อ

## 1. ปัญหาคืออะไร (เล่าแบบเด็ก)

ลองนึกภาพร้านขนมที่มีลูกค้าประจำ 7,000 คน ทุกเดือนจะมีลูกค้าบางคนเลิกซื้อแล้วไปซื้อร้านอื่น
เจ้าของร้านรู้ว่า **การหาลูกค้าใหม่มาแทน แพงกว่าการง้อลูกค้าเก่าให้อยู่ต่อ** มาก

ปัญหาคือ เจ้าของร้านไม่รู้ว่า **ใครกำลังจะเลิกซื้อ** ถ้ารู้ก่อน จะได้เอาขนมไปแถม ไปคุยดี ๆ ให้เขาอยู่ต่อ
แต่จะไปคุยกับทุกคน 7,000 คนก็ไม่ไหว

**โปรเจกต์นี้คือการสร้าง "เครื่องทำนาย"** ที่ดูข้อมูลลูกค้าแต่ละคน แล้วบอกว่า "คนนี้เสี่ยงจะเลิก 62%" หรือ "คนนี้เสี่ยงแค่ 3%" เจ้าของร้านจะได้ไปคุยกับคนที่เสี่ยงสูงก่อน

ในงานจริง ร้านขนมคือ **บริษัทโทรคมนาคม** (ค่ายมือถือ/อินเทอร์เน็ต) และการเลิกซื้อเรียกว่า **Churn** (เชิร์น)

## 2. ข้อมูลที่ใช้ (วัตถุดิบ)

| สิ่งที่ต้องรู้ | คำตอบ |
|---|---|
| เอาข้อมูลมาจากไหน | เว็บ Kaggle ชุดข้อมูลชื่อ Telco Customer Churn ที่บริษัท IBM ทำไว้ให้คนเรียน |
| มีลูกค้ากี่คน | 7,043 คน |
| แต่ละคนมีข้อมูลอะไรบ้าง | 19 อย่าง เช่น เพศ อายุการใช้งาน (กี่เดือน) รูปแบบสัญญา ใช้เน็ตแบบไหน จ่ายเดือนละเท่าไร |
| เฉลยคืออะไร | คอลัมน์ Churn บอกว่าคนนี้ "ย้ายค่ายแล้ว (Yes)" หรือ "ยังอยู่ (No)" |
| ย้ายค่ายกี่คน | 1,869 คน คิดเป็น 26.5% หรือประมาณ 1 ใน 4 |

**เปรียบเทียบ:** เหมือนมีสมุดจดประวัติลูกค้า 7,043 หน้า แต่ละหน้ามีข้อมูล 19 ช่อง และมีช่องสุดท้ายเขียนว่า "ไปแล้ว" หรือ "ยังอยู่" เราจะเอาสมุดเล่มนี้ให้คอมพิวเตอร์อ่าน แล้วให้มันหาว่า คนที่ "ไปแล้ว" มีอะไรเหมือนกันบ้าง

### ข้อมูลบอกอะไรตั้งแต่ยังไม่สร้างโมเดล

พอเอาข้อมูลมานับดูเฉย ๆ ก็เห็นแล้วว่า

| กลุ่มลูกค้า | ย้ายค่ายกี่ % |
|---|---|
| สัญญาแบบรายเดือน (เลิกเมื่อไหร่ก็ได้) | 42.7% |
| สัญญา 1 ปี | 11.3% |
| สัญญา 2 ปี | 2.8% |
| ใช้เน็ตไฟเบอร์ (แพง) | 41.9% |
| ใช้เน็ต DSL (ถูกกว่า) | 19.0% |
| ลูกค้าใหม่ ใช้มาไม่เกิน 6 เดือน | 52.9% |
| ลูกค้าเก่า ใช้มาเกิน 4 ปี | 9.5% |

**แปลง่าย ๆ:** คนที่ผูกสัญญายาว อยู่นาน ๆ แทบไม่ย้าย ส่วนคนที่เพิ่งมา จ่ายแพง และไม่ได้ผูกสัญญา คือกลุ่มที่พร้อมจะไปทุกเมื่อ

## 3. ขั้นตอนทั้งหมด 6 ขั้น (เหมือนทำอาหาร)

```
1. เข้าใจโจทย์และข้อมูล  →  2. ล้างและเตรียมข้อมูล  →  3. สร้างและคัดวัตถุดิบ (ฟีเจอร์)
        →  4. สร้างโมเดล 3 แบบ  →  5. วัดผลและปรับจูน  →  6. เอาไปใช้จริง (เว็บ)
```

### ขั้นที่ 1: เข้าใจโจทย์

โจทย์นี้เป็นแบบ **"แบ่ง 2 กลุ่ม"** (Binary Classification) คือตอบว่า ย้าย / ไม่ย้าย
แต่เราไม่ให้โมเดลตอบแค่ ใช่/ไม่ใช่ เราให้มันตอบเป็น **เปอร์เซ็นต์** เพราะทีมงานต้องเอาไป **เรียงลำดับ** ว่าโทรหาใครก่อน

**เปรียบเทียบ:** หมอไม่ได้บอกแค่ "ป่วย/ไม่ป่วย" แต่บอกว่า "เสี่ยง 80% ควรตรวจเพิ่มด่วน" กับ "เสี่ยง 5% ปีหน้าค่อยมา"

### ขั้นที่ 2: ล้างและเตรียมข้อมูล

ข้อมูลดิบมีปัญหา 3 อย่างที่ต้องแก้ก่อน

**ปัญหา 1: มีค่าว่างที่ซ่อนอยู่**
ช่อง "ค่าบริการสะสม" มี 11 คน ที่เป็นช่องว่างเปล่า ๆ (เคาะ space bar) คอมพิวเตอร์เลยคิดว่าเป็นข้อความ ไม่ใช่ตัวเลข
พอไปดูจริง ๆ ทั้ง 11 คนเป็น **ลูกค้าที่เพิ่งสมัครวันนี้** ยังไม่เคยจ่ายเงินเลย เราจึงใส่เลข 0 ให้ เพราะ 0 คือความจริง

**ปัญหา 2: คอมพิวเตอร์อ่านคำไม่ออก**
ข้อมูล 16 จาก 19 ช่องเป็นคำ เช่น "รายเดือน" "ไฟเบอร์" คอมพิวเตอร์คำนวณกับคำไม่ได้ ต้องแปลงเป็นตัวเลข
วิธีที่ใช้เรียกว่า **One-Hot Encoding** คือเปลี่ยน 1 ช่องคำ ให้เป็นหลายช่องที่มีแค่ 0 กับ 1

> ตัวอย่าง: ช่อง "สัญญา" มี 3 แบบ → กลายเป็น 2 ช่อง: [เป็น 1 ปีไหม? 0/1] [เป็น 2 ปีไหม? 0/1]
> ถ้าทั้งสองช่องเป็น 0 แปลว่ารายเดือน (ไม่ต้องมีช่องที่ 3 เพราะเดาได้ เรียกว่า drop first)

**ปัญหา 3: ตัวเลขคนละสเกล**
"อายุการใช้งาน" มีค่า 0 ถึง 72 แต่ "ค่าบริการสะสม" มีค่าถึง 8,000 ถ้าไม่ปรับ โมเดลจะคิดว่าตัวเลขใหญ่สำคัญกว่า
วิธีแก้เรียกว่า **StandardScaler** คือปรับทุกช่องให้อยู่สเกลเดียวกัน (ค่าเฉลี่ย 0)

**เปรียบเทียบ:** เหมือนเทียบคะแนนสอบวิชาที่เต็ม 10 กับวิชาที่เต็ม 100 ต้องแปลงเป็นเปอร์เซ็นต์ก่อนถึงจะเทียบกันได้

**แบ่งข้อมูลเป็น 2 กอง (สำคัญมาก)**
- กอง Train 80% = 5,634 คน ให้โมเดล "เรียน"
- กอง Test 20% = 1,409 คน เก็บซ่อนไว้ "สอบ" โมเดลตอนจบ

**เปรียบเทียบ:** เหมือนให้นักเรียนอ่านหนังสือ 80% แล้วออกข้อสอบจาก 20% ที่ไม่เคยเห็น ถ้าเอาข้อสอบให้ดูก่อน คะแนนจะสูงแต่ไม่ได้แปลว่าเก่งจริง
กฎเหล็กคือ **ห้ามให้กอง Test รั่วไปในการเรียนเด็ดขาด** ศัพท์เรียกว่า No Data Leakage

### ขั้นที่ 3: สร้างและคัดวัตถุดิบ (Feature Engineering & Selection)

"ฟีเจอร์" (Feature) = ข้อมูลแต่ละช่องที่โมเดลใช้ทาย

**3.1 สร้างฟีเจอร์ใหม่ 2 ตัว** จากของเดิม เพราะคิดว่าน่าจะช่วย
- **Total_Addons** = นับว่าสมัครบริการเสริมกี่อย่าง (0 ถึง 6) คิดว่าคนที่สมัครเยอะน่าจะย้ายยาก
- **AvgMonthlySpend** = ค่าบริการสะสม ÷ จำนวนเดือน คิดว่าถ้าตอนนี้จ่ายแพงกว่าเฉลี่ยที่เคยจ่าย อาจอยากเลิก

**3.2 เช็คว่าซ้ำกันไหม (Correlation)**
พบว่า AvgMonthlySpend **ซ้ำกับค่าบริการรายเดือนถึง 95.6%** (ค่า 0.956 จากเต็ม 1) คือแทบเป็นตัวเดียวกัน
**เปรียบเทียบ:** เหมือนมีเพื่อน 2 คนที่ตอบเหมือนกันทุกครั้ง ถามคนเดียวก็พอ

**3.3 วัดว่าฟีเจอร์ไหนสำคัญจริง (Permutation Importance)**
วิธีวัดฉลาดมาก: **เอาช่องนั้นมาสลับค่ามั่ว ๆ** แล้วดูว่าโมเดลทายแย่ลงไหม
- ถ้าสลับแล้วแย่ลงมาก = ช่องนั้นสำคัญ
- ถ้าสลับแล้วเฉย ๆ = ช่องนั้นไม่มีประโยชน์ มีก็เหมือนไม่มี

**เปรียบเทียบ:** เหมือนทดสอบว่านักฟุตบอลคนไหนสำคัญ โดยลองให้คนนั้นเล่นมั่ว ๆ ถ้าทีมแพ้ทันทีแปลว่าคนนั้นสำคัญ ถ้าทีมยังชนะเหมือนเดิม แปลว่าไม่ได้ช่วยอะไร

ผลออกมาว่า **3 อันดับแรกคือ รูปแบบสัญญา (Contract), ประเภทเน็ต (InternetService), อายุการใช้งาน (tenure)** ตรงกับที่นับดูในข้อ 2 เลย
ส่วนที่ **ไม่มีประโยชน์** คือ เพศ, มีโทรศัพท์ไหม, ประกันอุปกรณ์, เป็นผู้สูงอายุไหม และ **Total_Addons ที่เราสร้างเอง**

**จุดที่ต้องระวังตอนวัด:** เราแบ่งกอง Train ออกมาอีกกองเล็ก ๆ เรียกว่า **Validation** (1,127 คน) ไว้ใช้วัดตรงนี้
เพราะถ้าเอากอง Test มาวัด แล้วตัดสินใจเลือกฟีเจอร์จากมัน ก็เท่ากับ **แอบดูข้อสอบ** ผลสุดท้ายจะเชื่อไม่ได้

**3.4 ผลก่อน-หลังคัด**

| | ก่อนคัด | หลังคัด |
|---|---|---|
| จำนวนฟีเจอร์ | 21 ตัว | 16 ตัว |
| คะแนน (ROC-AUC) | 0.8455 | 0.8460 |

**แปล:** ตัดทิ้ง 5 ตัว คะแนน **เท่าเดิม** (ต่างกัน 0.0005 ถือว่าเท่ากัน) แต่โมเดลง่ายขึ้น
**ห้ามพูดว่า "คัดแล้วดีขึ้น"** เพราะตัวเลขไม่รองรับ ให้พูดว่า "เท่าเดิมแต่ง่ายขึ้น"

**บทเรียนใหญ่:** Total_Addons ที่เราคิดว่าจะช่วย กลับได้อันดับสุดท้ายจาก 21 ตัว เพราะข้อมูลมันซ้ำกับ 6 ช่องบริการเสริมที่มีอยู่แล้ว
**สร้างอะไรขึ้นมาแล้วต้องวัดผล ไม่ใช่เชื่อว่ามันจะดี**

### ขั้นที่ 4: สร้างโมเดล 3 แบบ

โมเดล = "สมอง" ที่เรียนจากข้อมูลแล้วทาย เราลอง 3 แบบเพื่อดูว่าแบบไหนเหมาะ

| โมเดล | คิดแบบไหน | เปรียบเทียบ |
|---|---|---|
| **Logistic Regression** | ให้คะแนนแต่ละช่อง แล้วรวมกันเป็นความน่าจะเป็น | เหมือนแบบฟอร์มประเมิน ที่แต่ละข้อมีน้ำหนักต่างกัน รวมคะแนนแล้วบอกว่าเสี่ยงกี่ % |
| **Decision Tree** | ถามเป็นทอด ๆ "สัญญารายเดือนไหม? → ใช้มาน้อยกว่า 6 เดือนไหม? → เสี่ยงสูง" | เหมือนแผนผัง 20 คำถาม |
| **Random Forest** | สร้าง Decision Tree 200 ต้น แต่ละต้นดูข้อมูลคนละมุม แล้วโหวตกัน | เหมือนถามหมอ 200 คนแล้วเอาเสียงข้างมาก |

ทุกโมเดลตั้งค่า **class_weight = balanced** แปลว่า "ให้ความสำคัญกับคนที่ย้ายค่ายมากขึ้น" เพราะคนย้ายมีแค่ 26.5% ถ้าไม่ตั้ง โมเดลจะขี้เกียจแล้วทายว่า "ไม่ย้าย" ทุกคน

### ขั้นที่ 5: วัดผลและปรับจูน

**5.1 ทำไมไม่ใช้ "ความแม่นยำ" (Accuracy) ธรรมดา** ← นี่คือจุดที่กรรมการชอบถามที่สุด

ลองคิดดู: ลูกค้า 73.5% ไม่ย้ายค่าย
ถ้าโมเดลโง่ ๆ **ทายว่า "ไม่ย้าย" ทุกคน** โดยไม่ต้องคิดอะไรเลย ก็จะ **ทายถูก 73.5%** แล้ว
ดังนั้น Accuracy 74% ฟังดูดี แต่จริง ๆ อาจไม่ได้เก่งกว่าโมเดลโง่เลย

**เปรียบเทียบ:** ข้อสอบ 100 ข้อ ที่ 73 ข้อเฉลยเป็น "ข" คนที่กา "ข" ทุกข้อได้ 73 คะแนน ไม่ได้แปลว่าเก่ง

เราจึงใช้ **ROC-AUC** แทน มันวัดว่า "โมเดลแยกคนย้ายออกจากคนไม่ย้ายได้ดีแค่ไหน"
- 0.5 = เดาสุ่ม (โยนเหรียญ)
- 1.0 = แยกได้สมบูรณ์แบบ
- **เราได้ 0.85** = ดีกว่าเดาสุ่มมาก

**5.2 ผลของ 3 โมเดล**

| โมเดล | ROC-AUC ก่อนจูน | ROC-AUC หลังจูน |
|---|---|---|
| Logistic Regression | 0.8468 | 0.8455 |
| Decision Tree | 0.8277 | 0.8270 |
| Random Forest | 0.8412 | 0.8429 |

**5.3 การจูน (Hyperparameter Tuning)**
"จูน" = ลองปรับปุ่มตั้งค่าของโมเดลหลาย ๆ แบบ แล้วดูว่าแบบไหนดีที่สุด ใช้เครื่องมือชื่อ GridSearchCV ลองทุกชุดค่าให้อัตโนมัติ
**เปรียบเทียบ:** เหมือนปรับเสียงเบส-แหลมของลำโพงหลาย ๆ แบบ แล้วเลือกที่เพราะสุด

**ผลคือ จูนแล้วไม่ดีขึ้น** ทุกโมเดลเปลี่ยนไม่เกิน 0.002 ซึ่งเท่ากับไม่เปลี่ยน
**ทำไม:** (1) ค่าตั้งต้นดีอยู่แล้ว (2) ข้อมูลชุดนี้มีสัญญาณหลักแค่ไม่กี่ตัว ทุกโมเดลจับได้เหมือนกัน เพดานเลยอยู่ที่ 0.85
**ห้ามพูดว่า "จูนล้มเหลว"** ให้พูดว่า "จูนยืนยันว่าค่าที่ใช้เหมาะสมแล้ว"

**5.4 เลือก Logistic Regression** เพราะ
1. คะแนน ROC-AUC สูงสุด (0.8455)
2. อธิบายได้ว่าแต่ละช่องเพิ่มหรือลดความเสี่ยงเท่าไร
3. ไฟล์เล็กมาก (ไม่ถึง 10 KB) ทำงานเร็ว
4. Random Forest ได้ใกล้เคียง (0.8429) ต่างกันแค่ 0.003 ถือว่าเท่ากัน ก็เลือกตัวที่ง่ายกว่า

**5.5 โมเดลเก่งแค่ไหนจริง ๆ** (ดูจาก Confusion Matrix)

ในกอง Test 1,409 คน มีคนที่ย้ายค่ายจริง 374 คน

| | โมเดลจับได้ | โมเดลพลาด |
|---|---|---|
| คนที่ย้ายจริง 374 คน | 293 คน (78%) | 81 คน |
| คนที่ไม่ย้าย 1,035 คน | ทายถูก 749 | เตือนผิด 286 |

- **Recall 78%** = ในคนที่จะย้ายจริง เราจับได้ 78% (ดี)
- **Precision 51%** = ในคนที่เราเตือนว่าจะย้าย มีแค่ครึ่งหนึ่งที่ย้ายจริง (ต้องยอมรับ)

**เปรียบเทียบ:** เครื่องตรวจจับโลหะที่สนามบิน ดังทุกครั้งที่มีมีด (จับได้ 78%) แต่ก็ดังกับกุญแจด้วย (เตือนผิดครึ่งหนึ่ง)
ยอมรับได้ เพราะ **พลาดคนที่จะย้ายค่าย แพงกว่าโทรหาคนที่ไม่ได้จะไป** และเราให้เป็น % ทีมงานเลือกได้เองว่าจะโทรหาถึงระดับไหน

## 5. ศัพท์ที่ต้องรู้ (อธิบายแบบบ้าน ๆ)

| ศัพท์ | แปลว่า |
|---|---|
| **Churn** | ลูกค้าเลิกใช้บริการ ย้ายค่าย |
| **Feature** | ข้อมูลแต่ละช่องที่เอาไปทาย เช่น อายุการใช้งาน |
| **Target / เฉลย** | สิ่งที่อยากทาย คือ ย้าย/ไม่ย้าย |
| **Classification** | การทายว่าอยู่กลุ่มไหน (ต่างจากการทายตัวเลข เช่น ราคาบ้าน) |
| **Train / Test** | กองข้อมูลให้เรียน / กองข้อมูลไว้สอบ |
| **Validation** | กองเล็กที่แบ่งจาก Train ไว้ใช้ตัดสินใจระหว่างทาง โดยไม่แตะกอง Test |
| **Data Leakage** | ข้อมูลข้อสอบรั่วไปตอนเรียน ทำให้คะแนนดูดีเกินจริง |
| **One-Hot Encoding** | แปลงคำเป็นช่อง 0/1 หลาย ๆ ช่อง |
| **StandardScaler** | ปรับตัวเลขทุกช่องให้สเกลเดียวกัน |
| **Pipeline** | มัดทุกขั้นตอน (แปลงข้อมูล + โมเดล) เป็นก้อนเดียว |
| **Correlation** | ค่าบอกว่า 2 ช่องซ้ำกันแค่ไหน (1 = ซ้ำเป๊ะ, 0 = ไม่เกี่ยวกัน) |
| **Permutation Importance** | วัดความสำคัญของช่อง โดยสลับค่ามั่วแล้วดูว่าแย่ลงไหม |
| **Accuracy** | ทายถูกกี่ % จากทั้งหมด (หลอกได้เมื่อข้อมูลไม่สมดุล) |
| **ROC-AUC** | โมเดลแยก 2 กลุ่มได้ดีแค่ไหน (0.5 สุ่ม, 1.0 สมบูรณ์) |
| **PR-AUC** | คล้าย ROC-AUC แต่เน้นเฉพาะกลุ่มที่สนใจ (คนย้าย) เข้มงวดกว่า |
| **Recall** | ในคนที่ย้ายจริง เราจับได้กี่ % |
| **Precision** | ในคนที่เราเตือน มีกี่ % ที่ย้ายจริง |
| **Confusion Matrix** | ตาราง 2×2 นับว่าทายถูก/ผิดแบบไหนกี่คน |
| **Hyperparameter** | ปุ่มตั้งค่าของโมเดล ที่เราต้องเลือกเอง (โมเดลไม่ได้เรียนเอง) |
| **GridSearchCV** | เครื่องมือลองปุ่มตั้งค่าทุกแบบให้อัตโนมัติ |
| **Cross Validation (CV)** | แบ่งกอง Train เป็น 5 ส่วน สลับกันสอบ 5 รอบ เพื่อกันฟลุ๊ค |
| **class_weight = balanced** | บอกโมเดลให้สนใจกลุ่มเล็ก (คนย้าย) มากขึ้น |
| **Overfitting** | โมเดลจำข้อสอบเก่าได้แม่น แต่เจอข้อสอบใหม่แล้วทำไม่ได้ |
| **Deploy** | เอาโมเดลไปใช้จริง เช่น ทำเป็นเว็บ |
| **Flask** | เครื่องมือทำเว็บด้วย Python |
| **PythonAnywhere** | เซิร์ฟเวอร์ฟรีที่เอาเว็บ Python ไปวางได้ |
