# แผนนำเสนอโครงงาน: ระบบทำนายการยกเลิกบริการของลูกค้าธุรกิจโทรคมนาคมด้วย Machine Learning

เอกสารนี้คือ "แหล่งความจริงชุดเดียว" ของการนำเสนอ ตัวเลขทุกตัวตรวจกับ `telco_jed.ipynb` (รันล่าสุด),
รายงาน docx และเว็บที่ deploy จริงแล้ว ถ้าจะแก้ตัวเลขที่ไหน ให้แก้ที่นี่ก่อนแล้วค่อยไล่แก้สไลด์

สมมติฐาน: เวลานำเสนอ 10 นาที + ถาม-ตอบ 5 นาที ถ้าเวลาต่างจากนี้ ดูหัวข้อ "ปรับตามเวลา" ท้ายเอกสาร

---

## 1. หลักคิดในการออกแบบ

Rubric ส่วน Present มี 3 ข้อ: การนำเสนอ / การตอบคำถาม / ความเหมาะสม สไลด์จึงออกแบบตามนี้

| หลัก | ทำอย่างไร |
|---|---|
| หนึ่งสไลด์ หนึ่งประเด็น | หัวเรื่องแต่ละสไลด์เป็น "ประโยคสรุป" ไม่ใช่ชื่อหัวข้อ เช่น "สัญญารายเดือนยกเลิกมากกว่าสัญญา 2 ปี 15 เท่า" ไม่ใช่ "ผลการสำรวจข้อมูล" |
| ตัวเลขใหญ่ อ่านได้จากหลังห้อง | ตัวเลขสำคัญขนาด 60-96 pt ข้อความอื่นไม่ต่ำกว่า 24 pt ไม่เกิน 3 บรรทัดต่อสไลด์ |
| ซื่อสัตย์ก่อนถูกถาม | จุดอ่อน 3 เรื่อง (Tuning ไม่ช่วย, Total_Addons ถูกตัด, Precision 51%) พูดเองบนสไลด์ ดีกว่าให้กรรมการจับได้ |
| มีของจริงให้ดู | เว็บที่ deploy อยู่จริง แต่ **ต้องมีภาพสำรอง** เผื่อเน็ตล่ม |
| สไลด์สำรองสำหรับตอบคำถาม | 5 หน้าท้ายเล่ม ไม่พูดถ้าไม่ถูกถาม แต่เปิดได้ทันที |

### สไลด์ 12 เลือก Logistic Regression (60 วินาที)
- **ข้อความ:** หัวเรื่อง "เลือก Logistic Regression: จับลูกค้าที่จะยกเลิกได้ 78%" / ตัวเลข 2 ก้อน: Recall 78% / Precision 51% / บรรทัดล่าง: "เหมาะกับการจัดลำดับ ไม่ใช่ตัดสินขาด จึงแสดงเป็นระดับความเสี่ยง 4 ระดับ"
- **ภาพ:** `fig07.png` (Confusion matrix)
- **พูด:** "เราเลือก Logistic Regression เพราะได้ ROC-AUC สูงสุด ตีความได้ว่าตัวแปรไหนเพิ่มหรือลดความเสี่ยง และไฟล์เล็กมากไม่ถึง 10 KB จากตารางนี้ โมเดลจับคนที่ยกเลิกจริงได้ 293 จาก 374 คน คือ 78% แต่ในกลุ่มที่เตือน มีคนที่จริง ๆ ไม่ยกเลิกปนอยู่ครึ่งหนึ่ง Precision จึงแค่ 51% นี่คือข้อจำกัดที่เรารู้ และเป็นเหตุผลที่ระบบให้เป็นระดับความเสี่ยงให้ทีมเลือกเองว่าจะโทรหาถึงระดับไหน"

## 3. สไลด์สำรอง (5 หน้า ไม่พูดถ้าไม่ถูกถาม)

### สำรอง A: ทำไม Tuning ไม่ทำให้ดีขึ้น
- ตารางเต็ม: โมเดล / CV ROC-AUC / Test ROC-AUC ก่อน / หลัง / ผลต่าง (LR 0.8482 / 0.8468 / 0.8455 / -0.0013, DT 0.8271 / 0.8277 / 0.8270 / -0.0007, RF 0.8453 / 0.8412 / 0.8429 / +0.0017)
- 3 เหตุผล: ค่าตั้งต้นดีอยู่แล้ว / สัญญาณอยู่ที่ตัวแปรไม่กี่ตัว / CV กับ Test ใกล้กันมาก = ไม่ Overfit

### สำรอง B: ป้องกัน Data Leakage อย่างไร
- แผนภาพการแบ่ง: ข้อมูล 7,043 → Train 5,634 / Test 1,409 → Train แบ่งอีกเป็น ฝึกย่อย 4,507 / Validation 1,127
- Preprocessor fit เฉพาะ Train / Feature Selection ใช้ Validation / Test ใช้ครั้งเดียวตอนสุดท้าย

### สำรอง C: ทำไมไม่ใช้ SMOTE
- ใช้ class_weight='balanced' แทน เพราะไม่สร้างลูกค้าปลอม ไม่เพิ่มเวลาเทรน และให้ Recall 78% ซึ่งเพียงพอ
- SMOTE เป็นแนวทางต่อยอดที่ทดลองได้

### สำรอง D: Hyperparameters ที่ทดลอง
- ตารางที่ 6 จากรายงาน (ขอบเขตการค้นหาและค่าที่ดีที่สุด) จำไว้ว่า RF ได้ min_samples_split = 10

### สำรอง E: รายละเอียดตัวแปร 19 ตัว
- ตารางที่ 1 จากรายงาน เผื่อถูกถามว่าตัวแปรไหนหมายถึงอะไร
